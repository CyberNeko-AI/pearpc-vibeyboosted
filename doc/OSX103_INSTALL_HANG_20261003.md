# OS X 10.3 安装写盘期间卡死：现场与诊断进展

日期：2026-10-03。当前状态：完整追踪定位到 BAT 更新后软件 TLB 未失效；修复通过独立回归，用户于 2026-10-03 确认已成功完成安装并进入系统注册界面。以下按调查阶段保留证据，早期“起因未确定”描述对应当时进度。

## 已确认的两种现场

### 原始进程 18164（包含 UP-SAFEGUARD）

- 配置为 `ppccfg.osx`，PVR `000c0201`，512 MiB 客体 RAM。
- CPU 线程持续运行；主线程在 SDL 等待事件，CUDA 在条件变量等待。没有证据显示宿主磁盘 I/O 阻塞。
- PPC PC 为 `0001ee14`，内存指令 `48000000`（自循环）。
- 从安装光盘只读提取 `mach_kernel`，其符号表把这个地址定位为 `_panic+0x260`。
- 循环前输出字符串是 `panic: We are hanging here...`。
- 用现场 SDR1 `1fc0003f`、SR 和散列页表翻译栈，得到 `_panic -> _trap -> _thandler`。
- `_trap` 保存的 savearea 在 EA `1dfb2500` / PA `03bc9500`：SRR0 `00000000`，SRR1 `40009030`，exception `10`（XNU 指令访问异常索引）。这是一次跳到零地址的客户机异常，而非 PearPC 宿主崩溃。该次跳零的更早起因仍待定位。
- 完整 RAM、CPU 原始结构、元数据、实际内核、符号表存于 `/tmp/pearpc-panther-18164/`。没有修改进程的客体内存，也没有终止它。

### 去除强制改写后的进程 22756

- 使用独立 APFS 克隆镜像 `/tmp/pearpc-panther-18164/hd-clone.img`。
- 用户在该窗口开始安装后，CPU 停在 `0008aae0`，LR `00088dd8`，MSR `00001000`。
- 实際代码是 `mapDrainBusy`：读取映射 flags 顶部字节，等到 busy == 1 后返回。
- r3 = `049fbac0`，该地址 flags = `03000001`，r4 = 3；调用者 `_hw_rem_map` 正准备移除映射。
- 这次没有经过 busy 强制修正，保留了未被修正的计数异常。完整 RAM/CPU 在 `/tmp/pearpc-panther-22756/`。
- 计数 3 本身不足以证明是 `lwarx/stwcx.`、JIT 分支、MMU 还是客户机控制流的问题。必须追踪进入此状态前的配对增减。

## 对现有实现的处理

删除 generic 和 AArch64 的 `mapDrainBusy` 指令序列识别与强制修正：它把客户机映射 busy 计数写成 1，并改写 r4。普通 PPC `b` 指令不应有这些副作用。即使它能让一次等待结束，也不能据此认为映射可以安全释放。

这个钩子曾随 `ecddbe0` 提交；此前将整个提交描述为 reservation 修复是不完整的。本次明确撤掉这个 OS 专属行为。撤掉它只消除了掩盖错误的代码，不是引用计数失衡的完整修复。

新增 `test/test_branch_state.cc`，执行真实 AArch64 跳转生成器，使用相同指令序列、5 种 busy 值、片段剩余空间 4..512、前后非连续片段。测试钩子 sentinel 用于发现旧生成器的非法调用，不模拟 MMU。

验证：

- 旧 HEAD 的 `ppc_alu.cc` 单独编译后运行新测试：`FAIL: branch changed guest state (busy=0, calls=1)`。
- 删除钩子后：1,280 次分支执行全部通过。
- 现有 3,072 次 `stwcx.` 片段边界执行和 13 项 ELF 测试通过。
- 上述测试不是安装成功的证据，也不是完整的 PowerPC 一致性认证。

## 未知 opcode 警告的边界

`7c000164` 的 XO 为 178（`mtmsrd`）；`78e8f80e` 是主 opcode 30 的 64 位旋转类指令。内存中它们位于按处理器能力选择的 32/64 位分支中，例如 `0009f9bc` 条件分支绕过 `0009f9c0` 的 64 位路径，`0009fa18` 绕过 `0009fa1c`。

当前 warning 来自代码生成阶段，不能证明指令在运行时被执行。本次实际卡点是 `mapDrainBusy`，原始 panic 保存区是跳到地址零的 ISI，而不是这两个地址的非法指令异常。没有为了消除警告而把它们实现成 no-op。

### 与实际内核代码对应

实际光盘内核 `_bcopy_physvir` 在 `00094854..00094864` 临时写 DBAT0/1，
建立复制所用的映射；复制返回路径在 `00094c50/00094c54` 把 DBAT0U/DBAT1U
置零，随后 `sync; isync; blr`。期间访存会填充模拟器软件数据 TLB。

AArch64 的 `ppc_opc_batu_helper` / `ppc_opc_batl_helper` 原先只更新 BAT 字段，
没有使软件 TLB 失效。撤销临时 BAT 后，旧的 identity write-cache 条目仍可能命中；
没有对应条目的 read-cache 走页表翻译，因此同一 EA 的读和写会落到不同物理页。
这与上面的日志以及 busy 泄漏吻合。不是通过把 IDE warning 或非法 opcode 当 no-op 修复。

### 修改与独立验证

- 每次 BAT 上半/下半写入后清空软件 TLB 标签。
- BAT 上半的 BL 改变时同时重算 BRPN，避免仍使用旧块大小的物理掩码。
- `mtspr` 修改 BAT 或 SDR1 后从 npc 重新分发，避免 IBAT 改变后继续旧物理页的机器码。
- 删除 UP-SAFEGUARD 的改动继续保留，没有重新加入计数修正。

`test_bat_tlb.S` 在修复前二进制稳定返回 6（六项检查失败），修复后返回 0。
`test_bat_code.S` 在修复前二进制 20 秒超时，修复后返回 0；它检查下一条指令
必须来自更新后的 IBAT 映射。对应 ELF 已生成，并加入常规测试列表。

最终验证：15 项裸机 ELF 全部通过，3,072 项 stwcx 片段测试和 1,280 项分支状态测试通过。
